# Research Claude Code synthetic conversation format: edge cases, gaps, and breakage risks. We proved that injecting a JSONL file into ~/.claude/projects/{path}/ with user/assistant message pairs and resuming via 'claude -p --resume {id}' works — Claude sees the synthetic history and responds in context. Now need to explore: (1) What happens with --output-format json and stream-json — do we get the response on stdout? (2) Does --session-id work for fresh sessions with predictable IDs (vs --resume for existing)? (3) What about system prompt injection — does Claude Code inject its own system prompt, or can we control it via --append-system-prompt alongside --resume? (4) Are there any fields that get validated (signatures on thinking blocks, requestId format, model ID)? (5) What happens when context gets long — does Claude Code's automatic compression work on synthetic history? (6) Tool use round-trips — can we inject synthetic tool_use + tool_result pairs? The tool_result is type 'user' with toolUseResult metadata. (7) Permission mode interactions — does permissionMode in the JSONL affect subsequent behavior? (8) Multi-turn: does the parentUuid chain need to be strictly linear or can there be branches (isSidechain)? (9) Concurrent access — what happens if cranium writes to the JSONL while claude -p is running? (10) Does the cwd in messages need to match the actual working directory? (11) Version field — does it need to match the installed claude version? (12) The slug field appears on some messages — is it required? (13) How does --no-session-persistence interact with --resume? Research should include reading Claude Code source if available, testing edge cases, and documenting findings.
